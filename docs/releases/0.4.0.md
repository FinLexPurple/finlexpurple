# FinLexPurple 0.4.0 — Pivot

**Published to PyPI:** https://pypi.org/project/finlexpurple/0.4.0/

`0.4.0` (codename *Pivot*) is the first **stable** release of the 0.4.0 line. It
promotes the `0.4.0b2` beta to PyPI and adds the Phase 4 interactive chat
experience. Install it with a single ordinary command, into a fresh virtual
environment:

```
pip install finlexpurple
```

Then `finlexpurple --help` should run clean.

> Unlike the `0.4.0b2` beta (TestPyPI only, two-step install), the stable release is
> on PyPI and installs normally — there is no TestPyPI dependency-confusion hazard to
> work around.

## What shipped

Everything in the `0.4.0b2` beta, now stable on PyPI, plus:

- **Interactive chat agent** (`finlexpurple chat`) — a hardened, scrollback-
  preserving terminal session over the same engine as the CLI. The agent
  autonomously decides which existing, already-gated operation to run, or you drive
  them directly with `/scan`, `/run`, `/agents`, and `/verify`. Scanning runs through
  the same scope confirmation, default-deny egress, budget cap, and approval gate as
  `scan`; nothing in chat loosens a gate or a cap.
- **Chat always-ask gate** — in chat, *every* state-changing probe pauses for the
  human's `y/N`, standard and hard-gated alike, regardless of `REQUIRE_HUMAN_APPROVAL`.
  A deliberate tightening, because the model — not a typed command — chose the
  operation. Hard-gated categories (banking, teller, vault, MCP) remain
  non-overridable.
- **Chat quality of life** — persistent input history across sessions and `Ctrl-C`
  to cancel an in-flight turn without ending the session.
- **Wordmark render fix** — the session-screen wordmark now uses a single-glyph
  FULL-BLOCK font, so it renders cleanly in color on terminals that draw
  ambiguous-width glyphs two cells wide.

Carried from `0.4.0b2`: the gated financial verification classes (Phase 2 — order
IDOR, coupon abuse, payment-status trust, refund abuse, race condition) and the
machine-readable report emitters (Phase 3 — SARIF 2.1.0, CycloneDX 1.6, SPDX 2.3),
each verified only by an in-scope read-back and validated offline against vendored
official JSON Schemas.

See [CHANGELOG.md](../../CHANGELOG.md) for the full entry.

## Release integrity — verifying the PEP 740 attestations

The release workflow publishes with **Trusted Publishing** (OIDC, no stored API
tokens) via `pypa/gh-action-pypi-publish@release/v1`, which attaches **PEP 740
Sigstore attestations** to each distribution by default. Anyone can verify, from a
clean machine, that a downloaded wheel/sdist was built and published by this
project's release workflow — no secret or prior trust required.

Install the verifier and fetch the distribution from PyPI:

```
pipx install pypi-attestations        # or: pip install pypi-attestations
pip download --no-deps --no-binary :all: "finlexpurple==0.4.0" -d ./dist
```

Verify each file against the GitHub Actions identity that published it — the
`release.yml` workflow in this repository, running under GitHub's OIDC issuer:

```
python -m pypi_attestations verify pypi \
  --repository https://github.com/FinLexPurple/finlexpurple \
  ./dist/finlexpurple-0.4.0*.whl ./dist/finlexpurple-0.4.0*.tar.gz
```

A passing check confirms the artifact's Sigstore attestation chains to this
repository's `release.yml` on a release tag. A failure — a missing attestation, a
mismatched repository, or a tampered file — means the artifact is **not** a genuine
release and must not be installed.

> The exact `pypi-attestations` subcommand/flags track that tool's current release;
> run `python -m pypi_attestations --help` if your installed version differs. The
> trust anchor never changes: the attestation must chain to
> `FinLexPurple/finlexpurple`'s `release.yml` under GitHub's OIDC issuer.
