# FinLexPurple 0.3.0 — Milestone M3

**Released to PyPI:** https://pypi.org/project/finlexpurple/0.3.0/

0.3.0 is the first release in which `finlexpurple scan` runs the web path
end-to-end: it discovers endpoints, runs the web detectors, **verifies** findings
by deterministic replay, and writes a full report — with a signed evidence
bundle per verified finding.

## What shipped in M3 (Phases 11–14 + end-to-end scan wiring)

- **Deterministic verification engine** (Phase 11) — a finding is `verified` only
  when a replay reproduces it in code (SQLi error reproduction, SSRF out-of-band
  canary, IDOR two-session diff, XSS via a headless-browser runner), never on an
  LLM's confidence. Human-facing claims must pass quote-grounding.
- **Signed evidence bundle + `verify-bundle`** (Phase 12) — a reproducible
  per-finding bundle (request/response, replay log, canonical hash; Sigstore/
  cosign signature when online, hash-only offline) that a third party can
  re-verify **standalone and fully offline**.
- **Supply-chain module** (Phase 13) — wraps OSV-Scanner and pip-audit and adds
  original slopsquat / hallucinated-dependency, payment-SDK typosquat, and
  secrets detection.
- **Container module** (Phase 14) — wraps Trivy, Grype, Dockle, and hadolint and
  adds exposed-Docker-socket and container-escape-class checks; the module never
  mounts the host socket and never runs privileged.
- **End-to-end `scan` wiring** — the web detectors + verification engine +
  reporting engine are connected to `scan`, so a plain `scan --target <url>`
  produces findings and a report (`report.json`, `report.md`, `evidence/`,
  `replay-logs/`).

## Demonstrated result (0.3.0 target app)

A scan of the deliberately vulnerable 0.3.0 target application:

```
Recon: discovered 6 endpoints.
Scan complete: 18 findings (4 verified) across 6 detector calls.

summary: total 18, verified 4, verified_percent 22.2
         by_severity {critical 0, high 4, medium 2, low 6, info 6}
         by_status   {verified 4, reported 14, human_confirmed 0}

verified  sqli  http://127.0.0.1:5000/lookup
verified  ssrf  http://127.0.0.1:5000/settings/fetch-logo
verified  sqli  http://127.0.0.1:5000/login
verified  sqli  http://127.0.0.1:5000/login
reported  idor  http://127.0.0.1:5000/lookup
reported  xss   http://127.0.0.1:5000/search
(+ 12 generic_misconfig, reported)
```

**4 findings were independently verified** — three SQL injections and one SSRF —
each re-executed by code, not asserted. The verified SSRF was confirmed by an
observed out-of-band canary callback.

## Known limitations (honest)

- **XSS and IDOR are reported, not verified, in a black-box scan.** Verifying
  XSS needs a real headless-browser runner and IDOR needs two authenticated
  sessions; in a plain `scan` neither collaborator is available, so those classes
  are surfaced as `[REPORTED]` rather than `[VERIFIED]`. (In the result above,
  the idor and xss findings are reported.)
- **The default-on *dollar* spend cap is not yet enforced.** The default-on
  iteration/tool-call cap and the per-target request kill-ceiling are enforced;
  the dollar cap lands in Phase 20. Bound run cost via the iteration caps.
- **Supply-chain and container surfaces are not auto-run by `scan` yet.** The
  Phase 13/14 modules are complete and tested but are invoked via their module
  entry points for now; `scan --include supplychain|container` wiring, and the
  whitebox CodeFix flow, are follow-ups.
- **Evidence-bundle signatures require cosign + connectivity.** Without them,
  bundles are hash-only — labeled as such, never overclaimed.
