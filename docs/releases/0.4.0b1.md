# FinLexPurple 0.4.0b1 — Pivot (beta)

**Published to TestPyPI:** https://test.pypi.org/project/finlexpurple/0.4.0b1/

`0.4.0b1` is the first **0.4.0 beta** (codename *Pivot*). It is published to
**TestPyPI only**; the PyPI Trusted Publisher is configured and pending for the
eventual stable `0.4.0`. Install the beta explicitly from TestPyPI:

```
pip install --index-url https://test.pypi.org/simple/ \
  --extra-index-url https://pypi.org/simple/ "finlexpurple==0.4.0b1"
```

## What shipped

- **Financial verification classes** (Phase 2) — order IDOR, coupon abuse,
  payment-status trust, refund abuse, and race condition. Each is a gated,
  replay-backed check on the one capability contract, verified **only** by an
  in-scope read-back, never by an LLM. The race-condition class is deliberately
  conservative: a **bounded, rate-limited, gated** concurrency harness that marks
  `VERIFIED` only on a deterministic double-processing read-back and otherwise
  reports an honest `INCONCLUSIVE` human-review lead.
- **Machine-readable report emitters** (Phase 3) — `--format sarif` (SARIF
  2.1.0), `--format cyclonedx` (CycloneDX 1.6), and `--format spdx` (SPDX 2.3),
  each a pure transform of the one report document. SARIF uses a `physicalLocation`
  only when a real source file exists (else a `logicalLocation`); the SBOM writers
  build components/packages from the frozen package URLs and emit nothing when the
  report carries no purls (never fabricated). All three validate offline against
  vendored official JSON Schemas — the air-gapped tool never fetches at runtime.

## Release integrity — verifying the PEP 740 attestations

The release workflow publishes with **Trusted Publishing** (OIDC, no stored API
tokens) via `pypa/gh-action-pypi-publish@release/v1`, which attaches **PEP 740
Sigstore attestations** to each distribution by default. Anyone can verify, from a
clean machine, that a downloaded wheel/sdist was built and published by this
project's release workflow — no secret or prior trust required.

Install the verifier and fetch the distribution from the index:

```
pipx install pypi-attestations        # or: pip install pypi-attestations
pip download --no-deps --no-binary :all: \
  --index-url https://test.pypi.org/simple/ "finlexpurple==0.4.0b1" -d ./dist
```

Verify each file against the GitHub Actions identity that published it — the
`release.yml` workflow in this repository, running under GitHub's OIDC issuer:

```
python -m pypi_attestations verify pypi \
  --repository https://github.com/FinLexPurple/finlexpurple \
  ./dist/finlexpurple-0.4.0b1*.whl ./dist/finlexpurple-0.4.0b1*.tar.gz
```

A passing check confirms the artifact's Sigstore attestation chains to this
repository's `release.yml` on a release tag. A failure — a missing attestation, a
mismatched repository, or a tampered file — means the artifact is **not** a
genuine release and must not be installed.

> The exact `pypi-attestations` subcommand/flags track that tool's current
> release; run `python -m pypi_attestations --help` if your installed version
> differs. The trust anchor never changes: the attestation must chain to
> `FinLexPurple/finlexpurple`'s `release.yml` under GitHub's OIDC issuer.
